## Written and checked locally

- The homepage now mounts the Bridge. It reads `/bridge/state`; existing `/hall/` and `/hud/` remain available. NEEDS YOU, RUNNING NOW, SINCE YOU LEFT, hall cards, GLANCE, Talk/Type, visit/dismissal persistence and basic keyboard navigation are implemented. Full command palette remains Wave 3.
- REVIEW actions use the existing approvals store and permission checks. Edit saves literal supported fields without execution; approval requires the reviewed revision. Serialized execution claims in the existing ledger stop duplicate/stale execution, including legacy resolver calls. Unknown outcomes cannot automatically retry. This is not a second approval inbox. It does not make unrelated whole-list KV writes transactional.
- QUESTION now pauses private-web tool work into a checkpoint in the existing ledger. Answering atomically claims the current revision and resumes the exact model/tool context, with current permission checks. Duplicate answers, stale revisions and old worker tokens cannot replay the continuation. Repeated questions from one job have distinct UI identities. History read/write failures are explicit and unreadable history is never replaced. Queued/background model-driven councillors and inline councillor scopes now retain their original tool restrictions on continuation. Removed permissions remain removed, schemas are refreshed from the current registry, and replies retain the real councillor display name. Routine continuations now retain the exact step index, prior results, run timestamp, date context and a fingerprint of the routine definition. The outer job stops before later steps or delivery; cron and manual run-now refuse a duplicate while it waits. The question becomes answerable only after the routine receipt is saved. Edits/disablement are checked before resumption, and the same execution record carries subsequent questions and the remaining step states.
- A queued councillor waiting for an answer is no longer logged or delivered as a finished report. Failed queued work likewise does not emit a successful councillor-finished event. Completed/failed/cancelled processing and expired execution leases appear in activity; expired work is explicitly unknown. Execution fencing tokens and saved checkpoints are excluded from the state-reader result.
- NOTIFY cards use recorded notifications and stable dismissal IDs. Real conversations, calendar, todos, cached weather, extension heartbeat and estimated recorded model costs are projected. Missing sources remain unavailable. Simulated trading stays labeled; unsupported metrics are absent.
- Hall cards use small captures of the existing real WebGL models. Starting three preview renderers delayed initial navigation. The later explicit Windows design goal now adds one asynchronously loaded selected realm to the Bridge; it disposes the previous renderer on switching. The halls retain full interactive scenes. This supersedes the earlier zero-renderer Bridge design, without adding three live card renderers. The capture script regenerates card previews from geometry and excludes surrounding controls.
- Talk supports browser dictation with typing fallback; mock recognition checks are not physical microphone acceptance. Draft handoff never automatically sends or starts paid inference.
- Existing tool-loop processing now writes actual round/request boundaries to the existing ledger. Concurrent jobs retain independent records. A heartbeat renews a 90-second execution lease; expired/failed/cancelled jobs cannot be displayed as actively running. Percentages count recorded processing steps, not elapsed time or overall goal completion. Handling a tool request is not a claim that its requested external action succeeded. No scheduler or SDK added. Pending questions remain available for seven days. Checkpoints are capped at 512,000 serialized characters and retained in the existing ledger; a cleanup policy still needs review before production. No additional KV writes for this tracking.
- Routines use task-specific steps from the stored routine, with percentages based on completed steps. The Windows continuation now initializes these plans at every ordinary start, with an atomic duplicate-start claim and one parent execution through councillors and batches. Terminal state follows the saved outer receipt. Interrupted progress acknowledgements remain unknown and block replay. The remaining steps recheck current permissions, normalize aliases for gating, and preserve untrusted-context approval requirements. Waiting does not reset the routine failure counter.
- If a resumed job submits a batch, it stays queued rather than done. The batch collector claims its continuation once and then resumes only subsequent steps; duplicate deliveries cannot repeat them. Original non-question batch behavior remains supported. The execution token is omitted from public routine receipts.
