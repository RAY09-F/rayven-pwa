HARD RULES — these override everything else in this file
--------------------------------------------------------
1. HELA'S MEMORY IS NEVER CLEARED. No endpoint, tool, cron or cleanup may
   delete or trim memory:longterm:hela, her history, or any persona's long-term
   memory. Compaction means "append a summary", never "remove originals". Do
   not re-add anything like /hela/forget-session. If a task in this file seems
   to need deletion, it doesn't — stop and ask.
2. Never rename or move a KV key, an agent id, a persona id, a tool name, or a
   secret name. Add new ones; leave existing ones alone.
3. No new npm dependencies. No build step. Nothing that makes the Chromebook do
   more work than it does today (2.7 GB RAM, no swap — heavy installs crash the
   whole container). If you believe a dependency is unavoidable, stop and
   explain in plain English why; do not install it.
4. Secrets: never print, log, or paste a secret value. Never create a .dev.vars
   file. When a new secret is needed, tell Rayan exactly this, filling in NAME:
        nano ~/secret.txt        (paste the value, Ctrl+O, Enter, Ctrl+X)
        npx wrangler secret put NAME < ~/secret.txt
        rm ~/secret.txt
   and wait for him to confirm before continuing.
5. KV WRITE BUDGET. A blown write quota once silenced every bot at the same
   time. So:
   (a) On the reply path (a message from Rayan on the web or Telegram), the
       only KV writes allowed are the ones that exist today, plus ONE write
       when an approval is created. Autonomy-log entries, audit lines, cost
       counters, delegation queue items, the taint flag and event spool all
       ride INSIDE the persona history object the reply already saves — a
       `_spool` ring buffer (last 50 entries) on that object. Zero extra
       writes.
       (a2) One exception: a tool Rayan explicitly invokes that changes HIS
       OWN data (shopping list, notes, reading list, habits, expenses,
       journal, rss_watch / job_watch, routine_enable_template) may make ONE
       write to that family's single key. These are bounded by how often he
       talks; budget them at 50/day in the table.
   (b) All bookkeeping for one cron tick — autonomy-log entries, audit lines,
       drained spool entries, queued events, "last checked" stamps — goes into
       ONE key `tick:YYYY-MM-DD:HHMM`, written once at the end of the tick,
       only if non-empty. Never a shared daily key with read-modify-write: KV
       is last-writer-wins and eventually consistent, so overlapping writers
       lose data.
   (c) A councillor's state key is written only when its duty actually DID
       something (sent, changed, traded, delegated). A no-op check writes
       nothing and does not count as a "run".
   (d) Trader stats keys update only when a trade closes; the equity curve is
       sampled once at market close. Routine run history lives inside
       routines:<id> (last 20 runs): one write per run, no separate history
       key. Hard cap 60 routine runs per day.
   (e) Ceiling: a counter of writes added by this file, kept in the tick key.
       When it passes 2,500 since 00:00 UTC, every writer added by this file
       stops until the next UTC day and Thor tells Rayan once. Conversation
       history writes are never blocked.
   Before every deploy, print a table: feature → worst-case KV writes/day.
   Everything new combined must stay under 3,000/day.
   If Phase 0.4 finds the Workers Paid plan is NOT active, STOP after Phase 0

PHASE 1 — CONTAINMENT (automation is not safe without this)
======================================================================
Check what already exists before building any of these. Build only what is
missing. The point: once councillors run unattended and read web pages, email
and Telegram, an injected page must not be able to make Asgard text someone,
post something, or leak memory.

1.1  Taint bit and provenance. One flag per conversation, stored inside the
     persona history object (Rule 5a). Set the moment any untrusted content
     enters the context: web fetch, search result, page read by the
     extension, email body, Telegram message that is not from Rayan's private
     chat (Rule 15), any social API response, any capability response. While
     tainted: SMS, calls, social posts, capability creation, long-term memory
     writes, and browser navigation to a new domain are queued as approvals
     (1.5) instead of executed. The approval shows the literal recipient, the
     literal body, and where the content came from ("derived from a page
     fetched at 14:02"). The model never writes the approval text.
     Define here, once, the provenance shape every memory write from now on
     carries: { source, persona, ts, trust } with trust one of
     'rayan' | 'trusted-tool' | 'untrusted-content'. Entries without a trust
     field are READ as 'legacy' and are never rewritten.

1.2  Egress allowlist for HELA's capabilities and any tool that can POST or
     send: KV list of allowed hosts (one key), deny by default, a tool to
     request adding a host that queues an approval. Keep every existing guard
     (https only, no private ranges, no metadata, never own host, no secrets
     in a capability, 12 s timeout, 6,000-char cap, 40 max).

1.3  Untrusted wrapping. Every tool result that carries outside content is
     returned JSON-encoded with a source label, and the instruction to the
     model about what to do with it goes as a text block placed AFTER the
     tool_result block in the same user message (that is the API's shape).

1.4  Audit log. Every tool call, memory write and outbound request produces
     one audit line: timestamp, persona, councillor if any, tool, parameter
     SHAPE and hash (never values), triggering_event_id chaining back to the
     input that caused it. On the reply path the line goes into the history
     object's _spool (Rule 5a); in cron it goes into the tick key (Rule 5b).
     Each tick drains every persona's spool entries newer than the previous
     tick's `lastDrained` stamp into the tick key without rewriting the
     history key. Ninety days from now the question "which page caused that
     action" must be answerable. Once a day, COPY tick keys older than 30 days
     into R2 under asgard/audit/YYYY-MM-DD.json; never delete the KV keys.

1.5  Approvals inbox. One KV key `approvals` (pending list, capped at 50).
     Tools: approvals_list, approve, reject. Each new approval is also sent to
     Rayan's private Telegram by the persona's bot as
     "[APPROVAL 1234] <what> — reply APPROVE 1234 or REJECT 1234". The
     Telegram handler honours those two replies only from Rayan's id in a
     private chat (Rule 15). Hard-confirm tools keep the live confirmation on
     top (Rule 8).

PHASE 2 — THE COUNCILS: TWENTY REAL SUB-AGENTS

Design principle: WRAP, DON'T DUPLICATE. Many councillor duties already exist
as code (watchlist checks, calendar, the paper-trading agents, Hela's vigil and
forge). The councillor becomes the face and the accountability for that job.
It gets its own small brain, its own narrow toolset, its own schedule and its
own state — it does not get a copy of logic that already exists.

2.1  New file src/lib/council.js — the registry. One entry per councillor:
       id            lowercase stable id, e.g. 'jane_foster'. Never changes.
       owner         'thor' | 'loki' | 'odin' | 'hela'
       name, role, theme   display only — from the rosters above
       tools         the exact tool names this councillor may call (map the
                     wedges in team.html's CONFIG to real tool names; Odin's
                     five get the paper-trading tools; Hela's five get her
                     tools and nothing else)
       prompt        a short system prompt (10–20 lines): who they serve,
                     what they do, how they report, what they never do
       tier          'free' | 'cheap' | 'owner'  (see 2.3)
       duty          the standing job, if any, as a schedule (Rule 14)
       stateKey      council:<owner>:<id>  — ONE JSON object: last run,
                     last result, counters, whatever the duty needs

     autonomy-log entry (spool on the reply path, tick key in cron) so the
